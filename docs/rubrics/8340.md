## Must-explain facts

1. **The performance problem is re-render frequency, not rendering cost.** Every
   pointer-move while drawing a new element called `mutateElement`, which bumps the
   scene's version number; `StaticCanvas` re-renders whenever that version changes.
   So the *entire* static scene repainted on every mouse-move of a draw gesture —
   the more existing elements, the worse. A walkthrough that says "drawing was slow"
   without naming the re-render trigger fails this fact.
2. **The fix has two parts that both must appear, not just one:**
   - `dragNewElement`'s `mutateElement` call now takes an `informMutation` flag;
     passing `false` while a new element is still being drawn means that mutation no
     longer bumps the scene version, so `StaticCanvas` stops re-rendering on it.
   - `Renderer.ts`'s `getRenderableElements` now explicitly **excludes** the
     in-progress new element (`newElementId === element.id → skip`) from what
     `StaticCanvas` draws at all — because a *separate* canvas now draws it.
3. **`NewElementCanvas` + `renderNewElementScene` is a genuinely new rendering path**,
   not a refactor of an existing one: a dedicated `<canvas>` layered above/alongside
   the static canvas, redrawn on its own throttled RAF loop, that draws *only* the
   element currently being created. A step should show this as an added node in the
   dependency map (canvas layering), not bury it inside a text description.
4. **`editingElement` → `editingTextElement` is a rename that narrows meaning, not a
   cosmetic one:** the field used to double as "the text being edited" AND (via the
   PR's own commit history) informally overlapped with "the element being created".
   Splitting them is what makes `newElementId` a distinct, correctly-scoped concept
   in `Renderer.ts`. Worth one sentence; does not need its own step.
5. **This PR has real commit-history detours** ("PoC for a new element canvas" →
   several refinements → "extend to elbow arrow as well" → "fix linear el state") —
   at least one dead-end/rejected-alternative or "detour" tag should appear if the
   analyzer can point to a specific commit that was later reworked; do not invent one
   if the commits don't clearly show it.
6. **Coverage: only the ~67 non-mechanical hunks need individual accounting**; the
   272 test/snapshot hunks must be in `skippedHunks` (or already excluded upstream by
   `classifyHunks`), never explained or listed one-by-one.
